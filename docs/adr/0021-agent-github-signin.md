# 0021: One-click GitHub sign-in for an agent

## Status
Accepted, 2026-11-26.

## Context
- Live test, 2026-11-26: in a project room, opening the planned issues failed with `common/github.NO_IDENTITY`:
  "cx-agent needs a GitHub sign-in … Its owner runs this in .hagency/app … gh auth login --web --insecure-storage".
  A shell command is no use to a newcomer on a phone.
- That message was also a second copy of the sign-in command in `client/github_signin.py`, and it had drifted:
  no `GIT_CONFIG_NOSYSTEM=1`, no private folder (R3).
- ADR 0020 already has a one-click path from the panel to an agent on its owner's computer: Update.

## Decision
### One recipe
`common/github_login.py` holds the agent's GitHub sign-in once: its folder `.gh/<agent>` (mode 700), gh's
environment (other logins' tokens removed, `GH_CONFIG_DIR`, `GIT_CONFIG_GLOBAL` in that folder,
`GIT_CONFIG_NOSYSTEM=1`), the flags (`--web --insecure-storage`), the shell line for a terminal (`command()`),
and the message types and result words. The connect line, the panel's button and docs/GITHUB_SETUP.md use it
(a test checks the doc's line).

### The click
1. The owner clicks **Sign in to GitHub** under the agent in My agents (any room's panel, or My Hagency).
   - Shown for an agent on its owner's computer that is online and says it isn't signed in.
   - `console.act("github_signin")` checks: the clicker's own agent (full ID), on their computer, online,
     its code has this (below), not signed in, one click per agent per minute, none under way.
2. @pm sends the agent a to-device message, `xyz.hagencylabs.agent.github`, with a click id.
3. The agent (`adapters/agents/agent_github.py`) acts only on that type, only from @pm's account (Synapse sets
   the sender). One sign-in at a time; a newer click from @pm stops the running one and starts again.
   - Already signed in: "already". No gh: "no_gh". A gh without `--insecure-storage`: "too_old_gh".
   - Else it runs `gh auth login --web` with the recipe's environment. `BROWSER`/`GH_BROWSER` are a no-op, so
     nothing opens on that computer, and stdin gets one newline.
   - It reads gh's output for the one-time code, accepts only `^[A-Z0-9]{4}-[A-Z0-9]{4}$`, and sends just that
     code to @pm, with the click id (`xyz.hagencylabs.agent.github.result`). No code within a minute: "failed".
   - Then it waits for gh, at most 15 minutes ("timeout"; gh is killed). Its result is one word, plus the GitHub
     username from `hosts.yml`'s `user:` line, validated. Nothing else gh prints is sent or logged. Then it sends
     its state again (below).
4. @pm shows the code and https://github.com/login/device only to the owner: in their My agents row
   (only they see their agents; with Copy, like the GitHub card) and in their private chat with @pm. It accepts a code or result only for the
   click still waiting, from that agent, with that id.
5. The row then says **GitHub: @login ✓**, or the result in plain words.

### Knowing which agents can
At each start the agent tells @pm its GitHub state (`xyz.hagencylabs.agent.github.state`: signed_in with its
login, none, or no_gh). @pm keeps it on the agent's entry (`registry.GITHUB`). An agent that never sent one runs
code from before this ADR: the row says updating it brings the button (ADR 0020's Update, or Update my agent).

### Rooms
`NO_IDENTITY` now says, in under 200 characters (what @pm shows of a failure): open the Hagency panel → My agents
→ Sign in to GitHub, then ask @pm again ("@pm retry" only resumes a paused issue, never a failed plan or card;
a failed filing adds "say '@pm show the plan' and approve it again", as the plan is kept). Rooms never get the command or a path (`redact.room_safe`). The row shows
terminal users the full command, generated by `github_login.command()`.

## Consequences
- **Device-code phishing:** a code shown to the owner is one their own agent asked GitHub for, on their computer,
  right after their own click. A compromised agent could send another code, but it already runs with its owner's
  access there. The words say to enter it only after clicking.
- **One sign-in, not two:** unlike the connect line (ADR 0017), this doesn't also link the account to the
  person. Connect GitHub does that.
- **Retry is by hand:** a step that failed before the sign-in stays failed; the owner asks again (a kept plan:
  "@pm show the plan" and 👍; a paused issue: "@pm retry #N").
- **The terminal line is for macOS and Linux shells.** Windows users click the button.
- **@pm keeps clicks in memory:** a restart forgets a code being shown. The owner clicks again, and the newest
  click wins on the agent: its running sign-in (gh) is stopped and a new one starts. @pm waits for a code longer
  than the agent's worst case (`github_login.PM_CODE_WAIT_S`), so a code that came is never refused as late.
- **An agent restart mid-sign-in** (an Update, a crash) kills its gh first (its pipe read to the end, at most
  5 seconds, so a full pipe can't hang the stop); its start report (`"startup": true`) then clears the waiting
  click on @pm, so the button comes back at once. A report sent after a click carries that click's `"id"` and
  clears nothing; a start report naming a click (one its first sync brought) keeps that click. An older agent's
  report has neither field and counts as a start. @pm's requests are listened for before the agent's first sync.
- **A username is not a sign-in:** the state is `signed_in` only if `gh api --hostname github.com user` (the
  agent's own folder and environment, at most 15 seconds) doesn't say the token is refused (GitHub's 401, or
  gh's exit 4 for no token). Refused: `none`, and the button shows. No answer (offline, slow): what the folder
  says, as before; a click then signs in again rather than say "already". gh's output is matched, never logged.
- **Older or Hermes agents:** an agent without this code gets one soft line ("Update it to get a Sign in to
  GitHub button here"); a Hermes agent (no bridge) gets no GitHub line. An offline one says to start it.

## Security / accepted risks
- A click queued while the agent was down is taken at its next start; @pm has dropped that click, so it ignores the code. gh then waits until a newer click replaces it (each new click cancels the old sign-in) or 15 minutes pass.
- **Every device of the agent's account gets @pm's request.** @pm sends to `"*"`, so an old installation of
  the same agent still signed in on another computer could answer with its own code. Matrix to-device messages
  carry no sender device, so @pm can't tell them apart. Mitigation: disconnecting an agent resets its password
  and signs its other devices out.
- **The terminal fallback assumes the default install.** `github_login.command()` uses `$PWD/.gh/<agent>` and
  the `gh` on `PATH`; an agent run with `GH_IDENTITY_ROOT` or `GH_BIN` overrides needs those set by hand.
- **The one-time code travels through Matrix:** in a to-device message from the agent to @pm, and in the
  owner's private chat with @pm. It is useful only with the owner's own GitHub sign-in on github.com within 15
  minutes, and the words say to enter it only after clicking.
